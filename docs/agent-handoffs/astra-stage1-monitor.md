# A1.3 — shared monitor orchestration

- Owner: Astra. Independent reviewer: Sol. Base: `899c64e` plus locally integrated A1.1/A1.2; A1.2 was independently approved by Sol and its snapshot verified before proceeding.
- Objective: move the single existing monitor loop, IMonitorService, AppStatusChangedMessage and one-second interval into Application. Preserve tick ordering, cancellation, sequential start/stop/restart and exception containment for message receivers.
- Allowed files: Application monitor service/interface/message/constants/logging; Application monitor tests; corresponding MAUI removals, constants, aliases, logging and DI registration; AGENTS, this handoff and stage ledger; integration of Sol's A1.2 review only.
- Contracts: the constructor uses Core's six existing monitor source/sink interfaces rather than MAUI marker interfaces. MAUI's explicit factory supplies the existing service instances. No extra monitor instance, Generic Host, Discord connection or game-data discovery. Start and StopAsync retain their existing sequential lifecycle usage, not a new concurrent-call guarantee. The service still does not dispose the injected sink; the host lifecycle separately clears/disposes Discord after stopping the monitor.
- Non-goals: changing Core, fixing pre-existing concurrent lifecycle semantics, extracting view models or remaining platform services, Linux composition, settings debounce/dispatcher/launcher/exit contracts, new packages.
- Acceptance: Debug/Release Linux solution builds, Core/Application tests, analyser output, Linux host Native AOT publish/resource regression. Synthetic tests exercise immediate first tick, one timer on duplicate Start, periodic ticks, receiver failure containment, cancellation and waiting for an in-flight tick, disposal and restart. No live socket or game access. Native Windows/macOS checks remain out of scope and unverified; host AOT does not certify Application native execution.
- Dependencies: existing Core interfaces, TimeProvider/PeriodicTimer, existing messenger/logging packages.
- Stop conditions: behaviour change required, new unresolved warnings, new production contract beyond those listed, or unexpected task-owned modifications. No worker edits, commits or pushes.
